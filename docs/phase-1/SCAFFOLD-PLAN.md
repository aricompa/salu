# Phase 1 scaffold plan

This is the target shape of the repo at the end of Phase 1, plus the order to get there. Brief 01 builds the foundation layer. Briefs 02 to 04 fill in the features.

## Starting point (as of 2026-09-28)

- `main` holds only the create-next-app scaffold (Next.js 16.1.6, React 19.2.3, Tailwind v4) plus a `.gitignore` fix.
- The February Sprint 1 prototype (restaurant login, onboarding, dashboard, menu builder, tables and QR) was never pushed. If Ari recovers it, it goes on branch `archive/sprint-1-prototype` for **reference only**. Phase 1 rebuilds on the hardened schema instead of porting that code, because:
  - its RLS let anyone update or delete any order (`orders` policy `for all using (true)`)
  - its QR codes encoded a one-off session id, so a printed code could never serve a second party
  - it used `middleware.ts` (renamed to `proxy.ts` in Next.js 16) and Tailwind v3 directives on a v4 install
- The hosted Supabase project `Salu` (`qrqopbzqbibdzjmxzmlg`) is paused and held only test data. Ari decides between restoring it and creating a fresh project (Phase 0 in the delivery plan). Either way the schema comes from `supabase/migrations/`, never from the dashboard SQL editor.

## Config details

**`package.json` scripts**
```json
{
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "lint": "eslint",
  "typecheck": "tsc --noEmit",
  "format": "prettier --write .",
  "test": "vitest run",
  "test:e2e": "playwright test",
  "db:start": "supabase start",
  "db:stop": "supabase stop",
  "db:reset": "supabase db reset",
  "db:test": "supabase test db",
  "db:types": "supabase gen types typescript --local > src/lib/db/types.ts",
  "check": "npm run lint && npm run typecheck && npm run test && npm run db:test"
}
```

**`.gitignore`**: keep `.env*`, and add `!.env.example` so the template can be committed.

**`.env.example`**
```bash
# Browser-safe (RLS protects data). Local values come from `supabase status`.
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_replace_me
# Public base URL used in QR codes and auth redirects
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

**`supabase/config.toml`** (edit after `supabase init`)
```toml
[auth]
site_url = "http://localhost:3000"
additional_redirect_urls = ["http://localhost:3000/auth/confirm"]
enable_anonymous_sign_ins = true      # diners

[auth.email]
enable_confirmations = true           # staff must confirm email (Inbucket catches mail locally)

[auth.rate_limit]
anonymous_users = 200                 # see note below
```
Note on `anonymous_users`: Supabase's default anonymous sign-in limit is IP-based (30 per hour). A busy restaurant puts every diner behind one Wi-Fi IP, so that default would lock diners out at peak. Raise it now, and add Cloudflare Turnstile in Phase 2 as the real abuse control. Check the exact key name against the CLI's generated `config.toml` before relying on it.

**`src/lib/env.ts`**: parse `process.env` with zod at import time. Fail loudly if a variable is missing, and refuse any server-only variable name that starts with `NEXT_PUBLIC_`.

**Security headers** in `next.config.ts` via `headers()`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and `X-Frame-Options: DENY` for `/restaurant/*`. Add CSP in Phase 3 together with the Stripe domains.

**CI (`.github/workflows/ci.yml`)** runs on every PR:
1. `npm ci`, then lint, typecheck, and `vitest run`
2. `supabase/setup-cli` action, `supabase start` (only db, auth and realtime needed), `supabase test db`
3. `next build` with placeholder public env vars
4. `gitleaks` secret scan

## Build order (Brief 01)

1. Tooling: scripts, prettier, vitest, playwright, `.env.example`, `.gitignore` fix
2. Supabase local: `supabase init`, config edits, drop in the existing migration and test, write `seed.sql`, `db:reset`, `db:test` green, `db:types`
3. Supabase clients plus `proxy.ts` (Next 16 convention), `env.ts`, `auth.ts` helpers
4. Design tokens plus base layout plus UI primitives (Button, Input, Card, Badge, Skeleton)
5. Staff auth: login and signup actions, email confirm route, signout route
6. Onboarding (`create_restaurant`) and portal shell with an empty dashboard and setup checklist
7. CI workflow plus one Playwright spec (sign up, confirm via local Inbucket, create restaurant, see dashboard)

Each step ends with `npm run check` green and a commit.
